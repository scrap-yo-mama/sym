# Bac à sable du code généré (INV7, tâche 1.5)

Spécification : CDC `08-specs-byo-securite.md` §3 (bac à sable) et §7, `15-strategie-tests.md` §7, `_index.md` INV7. Types : `@runtime/core` (`packages/core/src/sandbox/types.ts`). Tests : `sandbox.unit.test.ts` (borne de version, validation et fuzz des ponts, protocole), `sandbox.security.test.ts` (`assert_sandbox`, `pnpm test:security`).

## Architecture

- **`ProcessSandboxEngine`** (`engine.ts`) implémente `SandboxEngine { run(code, bridges, limits) }`. Un **processus enfant dédié par run**, lancé par `spawnPlan` : le lanceur change d'utilisateur (exécuté directement par le worker, voir ci-dessous), puis `/bin/sh` pose RLIMIT_CPU et, sous Linux, interdit tout vidage mémoire (RLIMIT_CORE d’un octet, que le noyau traite comme un refus même pour un collecteur en tube, et `coredump_filter` nul ; `assert_sandbox_no_core_dump`), `env -i` vide l'environnement (seul le canal IPC de Node passe), puis `node --no-node-snapshot --max-old-space-size=256 --permission --allow-addons --allow-fs-read=<script de l'enfant et paquets du moteur> child.js`. Chaque étape fait `exec` : le pid suivi reste celui de l'enfant. L'enfant déclare ses variables à `ready` ; toute variable hors celles que la plateforme injecte d'elle-même (macOS : `__CF_USER_TEXT_ENCODING`) fait refuser le run (`env_not_empty`). L'enfant est tué par `SIGKILL` à la fin de **chaque** run.
- **Utilisateur dédié** (D-30) : en production l'enfant tourne sous `sandbox` (uid 1500), distinct de `pwuser` (1001) qui porte `MASTER_KEY`, `DATABASE_URL` et les clés LLM. À uid égal, un code natif évadé de l'isolat lirait `/proc/<ppid>/environ` (PTRACE_MODE_READ accordé, même avec Yama) et le fichier de clé, `--permission` n'étant contrôlé qu'en espace utilisateur. Le changement d'uid passe par `SANDBOX_LAUNCHER`, un `setpriv` doté des seules capacités `cap_setuid,cap_setgid`, exécutable par le groupe `pwuser` seulement, appelé avec `--no-new-privs` : l'enfant (Node ordinaire, `SANDBOX_NODE`, sans capacités de fichier) n'en garde aucune et ne peut pas réutiliser le lanceur. Le lanceur est exécuté **directement par le worker**, jamais par un shell intermédiaire : sous `no-new-privileges` (Render), un exec ne garde de ses capacités de fichier que celles que l'appelant détient déjà, et le worker les détient parce qu'il tourne sous `node-worker`, copie de Node dotée de `cap_setuid,cap_setgid` (permises seulement : ni effectives, un `process.setuid(0)` du worker échoue, ni ambient) et réservée au groupe `pwuser` ; sous no-new-privileges, le lanceur garde les siennes par l'intersection avec ce permis ; l'uid dédié ne peut pas l'exécuter, d'où `SANDBOX_NODE=/usr/bin/node` pour l'enfant (constat F-20261001-R01, modèle complet dans `docs/deploiement.md`). Le worker ne peut pas signaler un processus d'un autre uid : l'arrêt forcé passe aussi par le lanceur (`killPlan`), en plus de `child.kill`. **Balayage** (`sweepPlan`) : quand le dernier run (ou la sonde) actif se termine, le lanceur envoie `SIGKILL` à tous les processus de l'uid dédié (`kill -1` sous cet uid), et aucun enfant n'est lancé avant la fin du balayage. Configuration : `SANDBOX_UID`, `SANDBOX_GID`, `SANDBOX_LAUNCHER`, `SANDBOX_NODE` (`sandboxOptionsFromEnv`, posées par `deploy/Dockerfile`). Avec `NODE_ENV=production`, le constructeur **refuse** un enfant sans uid ou sous l'uid du worker. `probeIsolation()` éprouve la frontière de l'OS (même lanceur, sans `--permission`) : `parentEnviron` doit valoir `denied` ; appelée au démarrage du worker en production par l'exécuteur de 1.6 (`exec/factory.ts`), qui refuse de démarrer sur `readable`. Vérifié le 2026-10-01 dans l'image Playwright 1.63 (noble) : `readable` sans utilisateur dédié, `denied` avec, `NoNewPrivs: 1`, `CapEff` nul ; sur l'image construite, sous le régime de Render et en Docker classique, par `tests/image/sandbox-privileges.image.test.ts` (`pnpm test:image`).
- **Enfant** (`child.ts`) : héberge l'isolat, ne fait ni réseau ni fichier, relaie les appels par IPC. Il est traité comme compromis : le parent valide chaque message (`protocol.ts`) et tue l'enfant sur message invalide.
- **Isolat** : une seule fonction de l'hôte y entre (`ivm.Callback` en mode `ignored`), aucune `Reference` ni objet de l'hôte (surface de GHSA-864f-rcv7-6rh4). Valeurs échangées en chaînes JSON. Globals retirés et piégés (`require`, `process`, `fetch`, `WebSocket`, `EventSource`, `navigator`, `WebAssembly`, `SharedArrayBuffer`, `Atomics`…) : un accès lève et journalise `sandbox_violation` (`forbidden_global`).
- **Ponts** (`bridges.ts`, côté parent) : `ctx.fetch(url, init)` (schéma, tailles, méthodes `GET`/`HEAD`/`POST` par défaut, en-têtes d'identité et de secret interdits, **domaines de l'API seulement**, redirections suivies par le pont avec contrôle du domaine **avant** chaque saut, garde SSRF à chaque connexion, `set-cookie` retiré), `ctx.log(...)`, `ctx.emit(item)`, `input`, et `ctx.page.*` (tâche 1.6, `exec/script.ts`) : liste fermée `goto`, `url`, `waitForSelector`, `content`, `textAll`, `attrAll`, `click`, `evaluate`, relayée par un second pont IPC (`call`, `bridge: 'page'`). `evaluate` envoie le texte de la fonction, exécuté dans la page (Chromium derrière le proxy d'egress et le verrou de domaines) ; une requête coupée par la politique de domaines (contexte de run ou proxy d'egress) vers un hôte que le site n'a pas contacté lui-même, une fois le code du script entré dans la page, est signalée par l'hôte (`SandboxRunOptions.watch`) et tue l'enfant ; les ressources tierces du site restent coupées sans verdict. Les valeurs rendues par `ctx.page.*` sont bornées dans la page avant transfert. Sans `allow_write_actions`, clic d'envoi et soumission refusés (`write_action_blocked`). En E3, `ctx.fetch` et les requêtes de la page passent par la cadence par domaine (1.9) et le plafond `max_requests_per_run`. Le texte de `ctx.log(...)` reste en mémoire pour l'essai (`onLog`) et n'est jamais écrit : le journal du worker et `run_logs` n'en reçoivent que le nombre de lignes et la taille (17 §6). L'annulation du run (`SandboxRunOptions.signal`) tue l'enfant. Quotas par run (requêtes, octets de réponse, éléments, journal).
- **Plafonds** : temps mur (`timeoutMs`, SIGKILL à l'échéance, y compris boucle après un `await` que le `timeout` d'isolated-vm ne couvre pas, issue #572) ; **temps CPU** (RLIMIT_CPU, `cpuLimitSeconds`, défaut 2 × `timeoutMs` + 5 s : SIGXCPU, rapporté `time_limit`/`cpu`) ; mémoire d'isolat (`memoryMb`, 128 par défaut, à valider) ; RSS du processus (`processMemoryMb`, défaut `3 × memoryMb + 192`, lue dans `/proc` sous Linux, déclarée par l'enfant ailleurs). `killLatencyMs` est mesuré sur la fin effective du processus.
- **Budgets côté hôte**, par run (la valeur émise se reconstruit dans le worker, qui détient les secrets) : éléments retenus `maxTotalItemBytes` (50 Mio) en plus de `maxItems` × `maxItemBytes` ; corps de réponse lus `maxTotalResponseBytes` (50 Mio, coupés puis refusés) ; journal `maxLogBytes` (64 Kio, dépassement = violation) ; octets reçus de l'enfant `maxIpcBytes` (128 Mio, chaque message compte au moins 256 octets) ; résultat `maxResultBytes` (10 Mio). L'enfant tient aussi un budget sortant et une file IPC de 64 Mio au plus : au-delà, `output_limit` plutôt qu'un tas saturé. Journal : au-delà de 4 Mio de `ctx.log` non remis au système (boucle de l'enfant affamée, aucun message ne partirait plus), l'enfant s'arrête lui-même par `SIGUSR2` et l'hôte rend `output_limit` ; `process.exit` est exclu (le fil d'isolat d'isolated-vm fait finir la sortie en SIGSEGV/SIGABRT).
- **Verdict** : **toute violation tue l'enfant aussitôt** (`outcome: 'violation'`), même si le script rattrape l'erreur : pas de boucle de violations, 32 violations retenues et journalisées au plus par run. Les sorties sans violation sont journalisées elles aussi : démarrage trop long ou moteur qui ne démarre pas (`child_crashed`). Un `import()` en clair est refusé avant lancement (`forbidden_import`) ; QuickJS signale tout import par son chargeur de modules ; isolated-vm, sans crochet d'import, ne signale qu'un import masqué (eval) non rattrapé. Un appel de pont lâché (promesse non attendue) est attendu avant le verdict.

## Version d'isolated-vm retenue : 7.0.1

Avis GHSA-864f-rcv7-6rh4 (critique, 2026-08-07) : versions `<= 7.0.0` affectées, **corrigées en 7.0.1 et 6.2.0**. Le CDC fixait 6.2.0 sur Node 24 et ≥ 7.0.1 sur Node 26 ; il est aligné sur 7.0.1 partout (D-24, 03 et 08 §3 §7). Constat terrain (2026-10-01) : 7.0.1 (`engines: >=24`) publie des binaires précompilés ABI 137 (Node 24) **et** ABI 147 (Node 26), glibc et musl, x64 et arm64 ; 6.2.0 s'arrête à ABI 137. 7.0.1 charge et passe `assert_sandbox` sur Node 24.21.0 et 26.10.0. Une seule version couvre donc la matrice sans second lockfile (pnpm n'installe qu'une version par importeur). `version.ts` refuse au démarrage du worker : 7.x < 7.0.1, 6.x < 6.2.0, 6.x sur Node ≥ 25, toute autre branche.

## Spike QuickJS (plan B, pas de production)

`quickjs-runner.ts` : `quickjs-emscripten-core` 0.32.0 + `@jitl/quickjs-wasmfile-release-sync` 0.32.0 (MIT), en **devDependencies**. Il tourne dans le même processus enfant, avec la même amorce et les mêmes ponts : la suite `assert_sandbox` passe sur les deux moteurs sans changer un pont (08 §7). Plafonds natifs : `setMemoryLimit`, `setMaxStackSize`, gestionnaire d'interruption à l'échéance.

Mesure locale (Apple M-series, Node 24.21, 3 essais, durée totale du run, démarrage de l'enfant ~50 ms compris) :

| Script | isolated-vm | QuickJS |
|---|---|---|
| trivial | ~49 ms | ~60 ms |
| boucle 2·10⁷ itérations | ~110 ms | ~1 000 ms |
| 20 000 objets, JSON aller-retour, filtre | ~57 ms | ~128 ms |

Soit ~15 fois plus lent en calcul pur, ~10 fois sur JSON (hors démarrage), dans la fourchette « 10 à 50 fois » du CDC. **Non retenu par défaut** : QuickJS pré-1.0 non audité, et la recette n'a pas encore ses scripts réels pour vérifier le plafond de temps. À réévaluer si isolated-vm casse sur une version de Node.

## Limites et risques résiduels

- **Réseau** (D-30) : pas d'isolation réseau au niveau de l'OS : l'enfant n'est placé dans aucun espace de noms réseau (D-30 a été décidé quand le seccomp par défaut de Docker refusait `unshare` et `CLONE_NEWNET` sans `CAP_SYS_ADMIN`). Le mode permission de Node 24 n'a **pas de filtrage réseau** (`--allow-net` arrive en Node 26) et `--allow-addons` l'affaiblit (avertissement `PERM0001`) : c'est une ceinture, pas une frontière. L'enfant n'ouvre aucun socket de lui-même ; la frontière réseau est l'absence de primitive dans l'isolat et le filtrage par le parent. Après une évasion, des sockets restent possibles (métadonnées cloud, PostgreSQL), sans secret à y présenter : à couvrir par la politique réseau de l'hébergeur (4.1).
- **Espaces de noms utilisateur** (F-20261002-02, D-56) : le profil seccomp du worker (`deploy/seccomp-chromium.json`, pour le bac à sable de Chromium) permet `clone`, `unshare` et `setns` sans filtre d'arguments à tout le conteneur, **enfant compris**. Après une évasion native (isolated-vm puis `--permission`), l'uid 1500 peut créer un espace de noms utilisateur (et, dedans, réseau, montage…) : aucun droit sur le worker, mais la surface du noyau dont dépendent beaucoup d'élévations de privilèges locales (nf_tables, montages) est ouverte. Risque accepté, tracé par `pnpm test:image` ; durcissement envisagé : filtre seccomp propre à l'enfant, posé par le lanceur avant l'exec de Node (refus de `unshare`, `setns`, `clone` avec `CLONE_NEWUSER`). Voir [docs/deploiement.md](../../../../docs/deploiement.md#risque-résiduel--espaces-de-noms-utilisateur).
- **Mémoire** : pas de RLIMIT_AS (v8 réserve plusieurs Go d'espace virtuel). Le plafond RSS est échantillonné toutes les 100 ms : un dépassement transitoire plus court passe. Hors Linux, la RSS est **déclarée par l'enfant**, donc non fiable après une évasion (développement seulement). Le canal IPC de Node lit un message entier avant validation : sa taille reste bornée par la RSS de l'enfant.
- **Lanceur** : il exige `CAP_SETUID` et `CAP_SETGID` dans l'ensemble limitant du conteneur (défaut Docker, accordées par Render) et un démarrage de l'image en root sans uid imposé (`user:`, `--user`, `runAsUser`) ; `no-new-privileges` est admis (régime de Render). Sinon le worker refuse de démarrer en production. Modèle complet : [docs/deploiement.md](../../../../docs/deploiement.md#modèle-de-privilèges-de-limage). Un `SIGKILL` envoyé par le lanceur vise un pid que Node n'a pas encore récolté.
- **Worker compromis** (D-32) : le worker détient `cap_setuid,cap_setgid` en permis. Compromis par du code natif (un script du bac à sable tourne sous l'uid 1500 sans capacité et n'y a pas accès), il peut les rendre effectives (`capset`) puis passer en **uid 0** : sous no-new-privileges, sans aucune capacité, mais propriétaire des fichiers de root (lecture de `/etc/shadow`, écriture de `/usr/local/bin/entrypoint.sh`, de `/usr/bin/node`, le `SANDBOX_NODE` des futurs enfants, et de `/app`). En compose (`restart: unless-stopped`), la couche inscriptible survit au redémarrage et l'entrypoint piégé s'exécute alors en vrai root, ce qui compromet aussi le server. Avant F-20261001-R01, c'était pire : en Docker classique, sans no-new-privileges, tout processus de `pwuser` (worker ou Chromium compromis) obtenait root avec toutes les capacités par `sandbox-launch --reuid=0 -- sh`. Atténuation : `read_only: true` et un tmpfs pour `/tmp` (recommandés dans `deploy/docker-compose.prod.yml`).
- **Uid dédié partagé** : tous les enfants, runs concurrents compris (`WORKER_CONCURRENCY`), tournent sous le même uid 1500. Le balayage de fin de run attend un instant sans run actif : sous charge continue, un processus détaché par un enfant évadé peut survivre jusque-là et observer les runs concurrents du même uid (`/proc/<pid>/*`, `ptrace` si Yama vaut 0 sur l'hôte), sans secret d'instance à lire (environnement vide). Un uid par emplacement de concurrence fermerait ce reste.
- Coût : un processus par run (~50 ms de démarrage). Pool recyclé après N runs : à valider (08 §3).
- `ctx.page.*` (Playwright relayé) et la tentative « `evaluate` qui exfiltre » : livrés en 1.6 (D-29), testés dans `tests/browser/executors.security.test.ts` (`assert_sandbox (ctx.page, D-29)`).
- Matrice CI : job `security` de ci.yml à chaque PR, Node 24 (suite complète) et Node 26 (suite du bac à sable), avec l'utilisateur dédié comme dans l'image, sans relance, rapport junit archivé en cas d'échec.
- Test RSS de 100 exécutions (échec isolé constaté au run 11, variante allocation mémoire, non reproduit en 360 exécutions sous charge) : deux chemins finissaient **sans** `sandbox_violation` (démarrage trop long sous charge, moteur qui ne démarre pas dans l'enfant, rendu `script_error`). Les deux journalisent désormais `child_crashed` ; aucun délai n'a été allongé.
